# ระบบบริหารตลาดบัญญัติทรัพย์

เว็บแอป (Responsive ใช้บนมือถือได้) สำหรับบริหารตลาด ครอบคลุมกระบวนการ 1.0–6.0 ตาม DFD พร้อม Machine Learning 2 ตัว:

1. **ทำนายความเสี่ยงค้างชำระ** (Classification: Logistic Regression / Random Forest) ใช้จัดลำดับการติดตาม และแจ้งเตือนล่วงหน้าเฉพาะผู้ค้าที่เสี่ยงสูง
2. **ตรวจจับค่ามิเตอร์ผิดปกติ** (Anomaly Detection: z-score + Isolation Forest) ตรวจก่อนออกบิลทุกครั้ง

รับชำระเงินผ่าน **QR PromptPay ของ Omise (Opn Payments) โหมดทดสอบ** และถ้ายังไม่ได้ตั้งค่า Omise ระบบจะใช้ผู้ให้บริการจำลองแทน จึงรันได้ทันที

## วิธีรัน

### แบบที่ 1: Docker (ง่ายที่สุด)

ต้องมี Docker Desktop

```bash
cp .env.example .env          # ถ้ายังไม่ใช้ Omise ไม่ต้องแก้อะไร
docker compose up --build
```

เปิด **http://localhost:8080** ครั้งแรก API จะสร้างข้อมูลตัวอย่างและเทรนโมเดลให้อัตโนมัติ ใช้เวลาประมาณ 10–30 วินาที

ถ้าต้องการล้างข้อมูลแล้วเริ่มใหม่ ใช้ `docker compose down -v` แล้ว `up` อีกครั้ง

### แบบที่ 2: รันแยกทีละส่วน (สำหรับพัฒนา)

ต้องมี Node.js 20+, Python 3.11+, PostgreSQL 16

```bash
# 1) ฐานข้อมูล
createuser -P market            # รหัสผ่าน: market
createdb -O market market

# 2) ML service  (terminal 1)
cd ml
python -m venv .venv && source .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -r requirements.txt
export DATABASE_URL=postgresql://market:market@localhost:5432/market
uvicorn app.main:app --port 8000

# 3) API  (terminal 2)
cd api
cp ../.env.example .env
npm install
npm run seed                    # สร้างตาราง + ข้อมูลตัวอย่าง + เทรนโมเดล
npm run dev                     # http://localhost:4000

# 4) Web  (terminal 3)
cd web
npm install
npm run dev                     # http://localhost:5173
```

## ตั้งค่า Omise (Payment Gateway โหมดทดสอบ)

1. สมัครที่ https://dashboard.omise.co แล้วอยู่ใน **Test mode**
2. ไปที่ **Keys** แล้วคัดลอก `pkey_test_...` และ `skey_test_...` ใส่ใน `.env`
   ```
   OMISE_PUBLIC_KEY=pkey_test_xxx
   OMISE_SECRET_KEY=skey_test_xxx
   ```
3. PromptPay ต้องเปิดใช้งานในบัญชี Omise ก่อน ถ้าสร้างรายการไม่ได้ให้ติดต่อ support ของ Omise เพื่อขอเปิด PromptPay
4. รีสตาร์ต API หน้าเข้าสู่ระบบจะแสดงว่า "ชำระเงิน: Omise (โหมดทดสอบ)"

**การทำงาน:** API สร้าง charge ด้วย `source[type]=promptpay` ในคำขอเดียว แล้วแสดง QR จาก `source.scannable_code` ผลการชำระมาได้ 2 ทาง

- **Webhook:** ตั้ง URL `https://<โดเมน>/api/webhooks/omise` ใน Omise Dashboard → Webhooks เมื่อได้ event `charge.complete` ระบบจะ**ดึง charge จาก Omise ซ้ำ**เพื่อยืนยันสถานะ ไม่เชื่อข้อมูลใน body โดยตรง ถ้ารันบนเครื่องตัวเองให้ใช้ `ngrok http 4000` แล้วใช้ URL ของ ngrok
- **Polling (สำรอง):** หน้าเว็บถามสถานะทุก 3 วินาที และ API จะถาม Omise ให้ จึงใช้ได้แม้ webhook ยังมาไม่ถึง localhost

**จำลองผลในโหมดทดสอบ:** ในหน้าชำระเงินมีปุ่ม "จำลอง: สแกนจ่ายสำเร็จ / ไม่สำเร็จ" ซึ่งเรียก `POST /charges/:id/mark_as_paid` หรือ `mark_as_failed` ของ Omise (ใช้ได้เฉพาะ test key) หรือจะกด Actions ใน Omise Dashboard ก็ได้ ปุ่มนี้ถูกซ่อนและ API ปฏิเสธคำขอเมื่อใช้ live key

> ขณะพัฒนาโปรเจคนี้ ทดสอบ flow ของ Omise จริงไม่ได้เพราะสภาพแวดล้อมที่ใช้เขียนโค้ดเข้าถึง api.omise.co ไม่ได้ ส่วนผู้ให้บริการจำลองทดสอบครบทุกขั้นตอนแล้ว โค้ด Omise (`api/src/services/payments/omise.js`) เขียนตามเอกสาร API ของ Omise ควรลองกับ test key ของตัวเองสัก 1 รอบก่อนนำเสนอ

## สคริปต์สาธิต (ประมาณ 10 นาที)

โหมดสาธิต (`DEMO_MODE=true`) ตั้งวันที่จำลองเป็นวันที่ 1 ของเดือนปัจจุบัน และมีปุ่ม **+1 วัน / +7 วัน** บนแถบด้านบน (เจ้าหน้าที่/เจ้าของ) ซึ่งเลื่อนวันและสั่งให้ "ระบบตั้งเวลา" ทำงานทีละวัน

1. **เจ้าหน้าที่ → จดมิเตอร์และออกบิล** กด "กรอกค่าจากเครื่องจดมิเตอร์" AI จะจับค่าผิดปกติ 4 แผง ได้แก่ A-03 น้ำสูง 3.2 เท่า, B-02 ไฟต่ำผิดปกติ, C-04 จดผิด (เลขน้อยกว่าเดิม) และ E-02 ไฟสูง ปุ่มออกบิลถูกบล็อกจนกว่าจะแก้ C-04 และติ๊ก "ตรวจหน้างานแล้ว" ที่เหลือ
2. ออกบิล 32 แผง ระบบให้ ML ประเมินความเสี่ยงของทุกบิลทันที
3. **ติดตามค้างชำระ** ดูตารางบิลที่เรียงตามโอกาสจ่ายช้าพร้อมเหตุผล แล้วกด **+1 วัน** ไปเรื่อย ๆ จะเห็นระบบเตือนล่วงหน้าเฉพาะผู้ค้าเสี่ยงสูง เมื่อเลยกำหนดเกิน 3 วันจะส่งต่อเจ้าหน้าที่และเจ้าของตลาด
4. **ผู้ค้า `a04`** เปิดบนมือถือแล้วชำระผ่าน QR (ตาม Sequence Diagram) เมื่อสำเร็จจะได้ใบเสร็จ และระบบแจ้งเจ้าหน้าที่ให้คืนน้ำไฟ (alt frame)
5. **เจ้าหน้าที่** กด "บันทึกคืนน้ำไฟ" แผง A-04
6. **ผู้ค้าขาจร** จองล็อกหน้าตลาดและชำระ QR โดยไม่ต้องสมัครสมาชิก ระบบกันจองซ้ำ
7. **เจ้าของตลาด** ดู Dashboard รายได้ 12 เดือน ยอดค้างชำระ แล้วไปหน้า **AI วิเคราะห์** เปรียบเทียบ LR กับ RF สลับโมเดล ปรับเกณฑ์ และกดเทรนใหม่

## Machine Learning

### 1) ทำนายความเสี่ยงค้างชำระ — `ml/app/risk.py`

- **Label:** 1 ถ้าบิลถูกชำระหลังวันครบกำหนด (หรือยังไม่ชำระและเลยกำหนดแล้ว) บิลที่ยังไม่ครบกำหนดไม่นำมาเทรน
- **ฟีเจอร์ (6 กลุ่ม)** คำนวณ ณ วันที่ออกบิล จึงไม่รั่วข้อมูลจากอนาคต

  | ฟีเจอร์ | ความหมาย |
  |---|---|
  | `late_count` | จำนวนครั้งที่จ่ายช้าใน 6 บิลล่าสุด |
  | `avg_days_late` | จำนวนวันที่ช้าเฉลี่ยต่อบิล |
  | `bill_ratio` | ยอดบิลนี้ ÷ ค่าเฉลี่ย 3 บิลก่อน |
  | `tenure_years` | ระยะเวลาที่เช่ามา |
  | `stall_type` | ประเภทแผง (one-hot) |
  | `season` | ฤดูกาลของวันครบกำหนด: เทศกาล / เปิดเทอม / หน้าฝน / ปกติ (one-hot) |
  | `early_days_avg` | จ่ายก่อนวันครบกำหนดเฉลี่ยกี่วัน (บิลที่จ่ายตรงเวลา) |
  | `seen_rate` | สัดส่วนบิลที่ผู้ค้าเปิดดูในแอปก่อนครบกำหนด (`bills.seen_at` บันทึกเมื่อผู้ค้าเปิดหน้าบิล) |
  | `app_share` | สัดส่วนบิลที่จ่ายผ่านแอป ไม่ใช่เงินสดที่สำนักงาน (`payments.provider`) |

  สามตัวหลังเป็น "พฤติกรรมการจ่าย" คิดจาก 6 บิลล่าสุดเฉพาะสิ่งที่เกิดก่อนวันออกบิล ใช้แทนวินัยของผู้ค้าที่ระบบมองไม่เห็นได้บางส่วน

- **โมเดล (เลือกใช้ได้หนึ่งตัวในหน้า AI):** `StandardScaler + OneHotEncoder` แล้วตามด้วย
  - `LogisticRegression` (lr)
  - `RandomForestClassifier(300 ต้น, max_depth=10, min_samples_leaf=10)` (rf)
  - `ExtraTreesClassifier` ขนาดเดียวกับ RF (et)
  - `HistGradientBoostingClassifier(max_depth=3, learning_rate=0.03, 100 รอบ, min_samples_leaf=20)` (gb)
  - โมเดลรวม: ค่าเฉลี่ยความน่าจะเป็นของ LR + RF + GB (ens) ประกอบจากโมเดลที่เทรนแล้ว ไม่เทรนซ้ำ
- **การประเมิน:** แบ่ง train/test 75/25 แบบ stratified และทำ 5-fold cross-validation (ทุกโมเดลใช้พับเดียวกัน) หลังประเมินแล้วเทรนใหม่ด้วยข้อมูลทั้งหมดเพื่อใช้งานจริง

**ผลการวัดกับข้อมูลตัวอย่าง** (507 บิล อัตราจ่ายช้า 37.7%, test 127 บิล, เกณฑ์ 0.5)

| โมเดล | Accuracy | Precision | Recall | F1 | ROC-AUC (test) | ROC-AUC (5-fold CV) |
|---|---|---|---|---|---|---|
| Logistic Regression | 0.709 | 0.657 | 0.479 | 0.554 | 0.713 | 0.749 ± 0.053 |
| Random Forest | 0.709 | 0.641 | 0.521 | 0.575 | 0.704 | 0.756 ± 0.036 |
| Extra Trees | 0.717 | 0.688 | 0.458 | 0.550 | 0.725 | 0.766 ± 0.051 |
| Gradient Boosting | 0.685 | 0.595 | 0.521 | 0.556 | 0.686 | 0.738 ± 0.031 |
| โมเดลรวม (LR + RF + GB) | 0.685 | 0.600 | 0.500 | 0.545 | 0.709 | 0.753 ± 0.040 |

ทุกโมเดลต่างกันน้อยกว่าความแกว่งของ CV (± SD) จึงสรุปไม่ได้ว่าตัวไหนดีกว่ากันบนข้อมูลชุดนี้ ระบบใช้ LR เป็นค่าเริ่มต้นเพราะอธิบายได้ง่ายที่สุด (ดูน้ำหนักฟีเจอร์ได้ตรง ๆ)
เมื่อทดสอบกับข้อมูลจำลอง 11 ชุด + ข้อมูลตัวอย่าง (CV 5×3) โมเดลรวมได้ AUC เฉลี่ยสูงสุด (0.751 เทียบ RF 0.748, LR 0.707)
แต่ต่างจาก RF อย่างไม่มีนัยสำคัญ (t = 0.66) ข้อดีจริงของโมเดลรวมคือไม่พลาดหนักในชุดไหน ด้อยกว่าการเลือก LR/RF ให้ถูกทุกชุดเพียง 0.006

ฟีเจอร์ที่มีผลมากที่สุด (LR) คือจำนวนวันที่ช้าเฉลี่ย ประวัติจ่ายช้า และช่วงเปิดเทอม ส่วนช่วงเทศกาลทำให้จ่ายตรงเวลามากขึ้น

**ข้อมูลสาธิตสองโปรไฟล์** (เลือกตอนรีเซ็ต: หน้าเจ้าของตลาด > เพิ่มเติม > สำหรับการสาธิตระบบ > รีเซ็ตข้อมูลสาธิต · `SIM_PROFILE=realistic|clear npm run seed` · หรือ `POST /api/admin/reseed` body `{ "profile": "clear" }`)

| โปรไฟล์ | ความหมาย | CV AUC (5 โมเดล) | Accuracy | เพดาน (รู้วินัยที่ซ่อน) |
|---|---|---|---|---|
| `realistic` (ค่าเริ่มต้น) | ความบังเอิญเท่าที่คาดในตลาดจริง | 0.82–0.85 | 0.80–0.82 | 0.861 |
| `clear` | ผลจ่ายช้าขึ้นกับปัจจัยมากขึ้น 3 เท่า (logit × 3) | 0.97–0.98 | 0.94–0.97 | 0.988 |

เพดาน Accuracy (ทายทางที่โอกาสสูงกว่าเสมอโดยรู้วินัยที่ซ่อนอยู่) ของ realistic อยู่ที่ราว 0.80 โมเดลชนเพดานแล้ว จึงเกิน 0.90 ไม่ได้ ส่วน clear อยู่ที่ราว 0.95
ตัวเลขของ `clear` สูงเพราะข้อมูลชัด ไม่ใช่เพราะโมเดลเก่งขึ้น ทุกหน้าที่แสดงผลจึงติดป้าย "ข้อมูลจำลอง · ความบังเอิญต่ำ"
ข้อมูลสาธิตทั้งสองแบบจำลองพฤติกรรมไว้ (วินัยดีจ่ายเร็ว เปิดดูบิลบ่อย จ่ายผ่านแอปมากกว่า ดู `api/src/lib/simBehavior.js`)
บนข้อมูลชุดเดียวกัน ปัจจัยพฤติกรรมเพิ่ม AUC ได้ +0.02 ถึง +0.03 ส่วนที่เหลือของตัวเลข realistic ที่สูงกว่ารุ่นก่อน (0.75) มาจากตลาดจำลองชุดใหม่ที่สุ่มได้เพดานสูงกว่า
ลองทำนาย 2 วันก่อนครบกำหนดแล้ว ไม่ช่วย: AUC ต่ำลง (0.75) และ accuracy ที่ดูสูงขึ้นมาจากบิลที่ยังไม่จ่ายตอนนั้นส่วนใหญ่จ่ายช้าอยู่แล้ว จึงไม่ได้ทำเป็นฟีเจอร์

**ทำนายจากไฟล์:** หน้า AI วิเคราะห์ แท็บ "ทำนายจากไฟล์" ให้ดาวน์โหลดไฟล์ CSV ตัวอย่าง กรอกข้อมูลบิลที่อยากรู้ แล้วอัปโหลดกลับ
ระบบตรวจทีละแถว ทำนายด้วยทุกโมเดลพร้อมเหตุผล สลับดูผลแต่ละโมเดลและดาวน์โหลดผลเป็น CSV ได้ ข้อมูลที่อัปโหลดไม่ถูกบันทึก

**การใช้งานในระบบ:** ทุกครั้งที่ออกบิล API ส่ง bill id ไปที่ `POST /risk/score` แล้วเก็บคะแนนและเหตุผลลงตาราง `bills` จากนั้นระบบตั้งเวลาจะเตือนล่วงหน้า 5 วันเฉพาะบิลที่ได้คะแนน ≥ เกณฑ์เสี่ยงสูง (ค่าเริ่มต้น 0.7) และหน้า "ติดตามค้างชำระ" เรียงลำดับตามคะแนน ผู้ค้าจะไม่เห็นคะแนนของตัวเอง

**ทำไมใช้เกณฑ์ 0.7:** ที่เกณฑ์ 0.6 ระบบจัด 14 จาก 32 รายเป็นเสี่ยงสูง ซึ่งมากเกินกว่าจะใช้จัดลำดับงานได้ เมื่อปรับเป็น 0.7 เหลือ 9 ราย ปรับค่านี้ได้ในหน้า AI

### 2) ตรวจจับค่ามิเตอร์ผิดปกติ — `ml/app/anomaly.py`

- **กฎพื้นฐาน:** เลขมิเตอร์น้อยกว่ารอบก่อน = จดผิด (บังคับแก้) และแผงที่ประวัติไม่ถึง 3 เดือนจะข้ามการตรวจ
- **z-score:** เทียบการใช้กับค่าเฉลี่ย 12 เดือนของแผงเอง (|z| > 3) และกับแผงประเภทเดียวกัน 3 เดือนล่าสุด (|z| > 4)
- **Isolation Forest** (200 ต้น, unsupervised): เวกเตอร์ 4 มิติ คือ log(ใช้/ค่าเฉลี่ยของแผง) และ log(ใช้/ค่าเฉลี่ยประเภทเดียวกัน) ทั้งน้ำและไฟ ใช้คะแนน anomaly score = `-score_samples()` (0–1) เกณฑ์ค่าเริ่มต้น 0.62
- **ผลกับข้อมูลตัวอย่าง:** จับได้ครบทั้ง 4 แผงที่ฝังไว้ (A-03 IF=0.686, B-02 0.615, C-04 จดผิด, E-02 0.709) และค่าปกติทั้งหมดมีคะแนนสูงสุด 0.522 จึงไม่มี false positive
- **ข้อจำกัด:** เป็นข้อมูลสังเคราะห์ ค่า precision/recall จริงต้องวัดกับข้อมูลตลาดจริงหลังใช้งาน ข้อมูลที่เจ้าหน้าที่ยืนยันใน `anomaly_logs` ใช้เป็น label สำหรับประเมินผลในอนาคตได้

**เทรนใหม่และดูรายงาน:** กดปุ่ม "เทรนโมเดลใหม่" ในหน้า AI หรือรัน `cd ml && python train.py` ประวัติการเทรนทุกครั้งเก็บในตาราง `model_runs`

### ข้อมูลตัวอย่าง

`api/src/seed/generator.js` สร้างประวัติ 17 เดือนของผู้ค้า 32 ราย (35 แผง, โซน A–E) แต่ละรายมี "วินัยการชำระ" ที่ซ่อนไว้ (`sim_discipline`) และมีผลของฤดูกาล ระยะเวลาเช่า และยอดบิล คอลัมน์ `sim_*` ใช้เฉพาะจำลองพฤติกรรมในโหมดสาธิต **ไม่ถูกส่งให้โมเดล** โมเดลต้องเรียนรู้จากประวัติการชำระเท่านั้น

**Sequence Diagram ชำระเงินผ่านแอป** (`docs/sequence_payment_app.drawio`) ตรงกับโค้ดดังนี้: เลือกบิล (`Bills.jsx`) → สร้างรายการชำระ (`billing.createPayment`) → ขอ QR จาก Omise → ผู้ค้าสแกนจ่าย → webhook/polling (`syncPayment`) → บันทึกการชำระและอัปเดตบิล (`applyPaymentResult`) → ออกใบเสร็จ → **alt [มิเตอร์เคยถูกตัดน้ำไฟ]** แจ้งเจ้าหน้าที่ให้คืนน้ำไฟ

## ข้อควรทำก่อนใช้งานจริง

- ตั้ง `JWT_SECRET` เป็นค่าสุ่มยาว และเปลี่ยนรหัสผ่านบัญชีทดลองทั้งหมด
- ตั้ง `DEMO_MODE=false` เพื่อใช้วันที่จริงและเปิด cron
- หน้า "การจองของฉัน" ของผู้ค้าขาจรค้นด้วยเบอร์โทรอย่างเดียว ถ้าใช้จริงควรเพิ่ม OTP
- ใช้ HTTPS และจำกัด CORS ให้เฉพาะโดเมนของตลาด
- เปลี่ยน Omise เป็น live key หลังผ่านการยืนยันตัวตนกับ Omise แล้วเท่านั้น
